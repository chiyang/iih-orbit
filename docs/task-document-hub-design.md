# 任務文件連結與儲存演進規劃

[文件索引](README.md) · [既有改版紀錄](next-release-design.md) · [目前資料儲存](data-storage.md) · [目前備份與同步](backup-and-sync.md)

討論日期：2026-10-13（Asia/Taipei）。同日補充：文件去重採識別碼優先已確認；側欄需求為直接瀏覽 Drive 目錄、導航並拖曳來源檔案，授權方案仍在討論。

狀態：使用者已確認先實作同步備份優化，文件連結尚未開始。儲存第一階段的已實作內容與限制見 [本機紀錄與雲端分塊備份](storage-sync-upgrade.md)；本文件其餘部分仍記錄未來文件功能與待決事項。

## 1. 已定案的產品方向

Orbit 作為以任務為導向的文件連結中心。使用者能從任務找文件，也能從文件找相關任務。文件與任務的關聯採多對多：一個任務能連結多份文件，同一份文件能連結多個任務。

| 項目 | 已定案方向 |
| --- | --- |
| 本機儲存 | 改為按紀錄保存，目標為 IndexedDB；保留離線任務操作及跨分頁寫入協調 |
| 雲端備份／同步 | 邏輯上維持全部工作空間的完整資料；實際保存改為資料分塊、未變區塊重用及版本索引 |
| 手動本機備份 | 保留單一 JSON 的匯入／匯出及目前還原操作；匯出檔須可獨立還原 |
| 文件與關聯 | 分開保存文件來源記錄及任務－文件關聯，支援雙向查找 |
| 任務操作 | 提供「加入文件」與「建立文件」；一個任務可以混合連結不同雲端服務的文件 |
| 文件建立 | 先選服務與檔案類型，再選該服務的保存位置；成功後建立任務關聯並開啟外部編輯／檢視入口 |
| 同時連線 | 架構支援 Google Drive、pCloud、Microsoft 365 同時連接；各服務功能分階段上線 |
| 備份服務 | 初期只使用 Google Drive；未來可擴充 pCloud 或 Microsoft 365，沿用相同備份及版本邏輯 |
| 文件內容 | 全部留在雲端服務；Orbit 及 Orbit 備份只保存來源連結、必要 metadata 和任務關聯 |
| 側欄文件 | 在 Orbit 右側側欄瀏覽 Drive 目錄，逐層導航到檔案，提供拖曳至主畫面建立任務及列表內「建立任務」按鈕；授權方案尚待決定 |

Orbit 管理來源連結與關聯，不讀取、編輯或整併連結文件的內容，也不處理共同編輯、內容版本或協作者權限。Google 文件／試算表／簡報等類型可由對應服務建立；實際編輯及協作由該服務負責。

「文件來源服務」與「Orbit 備份服務」是各自的設定。例如 Orbit 全部工作資料保存在 Google Drive，任務仍能同時連結 Drive 與 pCloud 文件。未來改用其他備份服務，不應改變任務連結文件的來源。

本輪明確調整先前構想：文件列表屬於 Orbit 側欄的功能；建立任務以側欄的拖曳與按鈕為入口，不以從 Drive／pCloud 網頁跨頁拖曳作為必要流程。跨頁拖曳不是本版驗收條件。

## 2. 本機 JSON 不變的範圍

使用者仍能下載一個 JSON，並以現有預覽、驗證、全部還原或加入工作空間流程匯入。雲端資料拆成多個區塊時，Orbit 負責組回所選範圍的完整邏輯資料，使用者不需自行收集區塊。沿用目前本機匯出範圍，本輪不取消選定工作空間的本機匯出。

不變的是檔案型態與操作語意。加入文件與關聯後，JSON 也需攜帶必要記錄，讀取、驗證及相容版本規則須一併更新。具體格式版本號尚未指定；舊備份仍需可讀，新資料不能交給不理解新欄位的舊程式寫回而遺失關聯。

儲存方案同時影響三個部分：

1. 瀏覽器本機的保存由整份 localStorage 記錄逐步改為按紀錄寫入。
2. 雲端由完整 JSON 版本檔改為版本索引與資料區塊。
3. 前端同步改為追蹤變動、取得必要區塊、驗證及整併，再以交易保存。

本輪不採用先前提及的 ZIP／多檔手動備份替代方案。現有單檔 20 MB 限制是否調整仍需討論；雲端分塊本身不會自動解決本機完整匯出的容量限制。

Orbit 的雲端區塊只包含工作空間、任務、共享設定、文件來源與關聯等 Orbit 資料。它們不包含外部文件內容、文件預覽本文、雲端服務的登入憑證或檔案下載內容。

## 3. 雲端分塊與版本完整性

以下原則已定案：

- 分塊只改變實際保存方式，每個可用版本仍代表全部工作空間的完整邏輯資料。
- 保留父版本與最近唯一共同祖先的判斷；不以電腦時間或最後修改時間決定內容勝負。
- 未改變的區塊可由新版本引用，不重複上傳相同內容。
- 新版本必須在所有必要區塊完成保存、完整性驗證後才成為可接續的版本。
- 多裝置並行保存仍可產生不同分支；不能只靠覆寫一個「最新版本」指標決定勝負。
- 歷史清理必須保留仍被保留版本、未處理分歧或待完成作業引用的區塊，以及必要的祖先資訊。
- 清理失敗與最新資料保存結果分開處理；已完整保存的版本不因歷史清理失敗而顯示保存失敗。

以下為建議的實作方式，尚未定案其具體格式：先保存有變動的區塊，再發布能完整描述該版內容的版本索引。兩台裝置同時發布時保留各自父版本，重新讀取並整併；任何索引都不應讓缺少區塊的版本被套用。

區塊可以先按工作空間劃分，大型工作空間再依穩定識別分組。避免一個任務就變成一個雲端檔案，造成大量小請求；具體粒度、最大大小及分組方式待效能量測後選定。前端也須減少整份複製、全量比較及全量校驗，只有拆分雲端檔案不足以減少本機處理成本。

沿用「最近八份」時，計數應是可還原的邏輯版本，不是實際雲端檔案數量。區塊回收已追加定案並實作：完整檢查無引用後觀察 30 天，閒置時每批最多 20 個移至垃圾桶；詳見備份優化紀錄。

## 4. 對同步速度的影響

必要區塊保存、驗證及最後發布索引會增加請求及計算成本；分塊不能保證每種情境都比完整 JSON 快。小資料集、首次同步或很多區塊同時改變時，額外請求可能使單次同步較慢。

日常少量修改則有機會減少打包、傳輸與整併的資料量。目標流程是只保存本次改動的區塊，確認後發布版本；保留已驗證的未變內容以減少重複讀取及校驗。

建議的效能措施，尚待實作與量測：

- 追蹤有變動的紀錄與區塊；保留已驗證的未變區塊及其校驗快取。
- 對新保存、首次讀取、缺少有效快取或出現異常的區塊完成必要驗證。具體上傳後驗證方式須另行決定，不能只檢查檔名或檔案存在。
- 適量合併區塊並限制並行請求數，避免大量小檔案抵銷傳輸量減少的收益。
- 歷史清理另行執行，不加入每次同步完成前必須等待的流程；清理本身仍須重新核對引用與雲端版本。
- 新版索引描述完整的當前區塊組合，避免日常讀取必須無限回放歷史變更；祖先關係另外保留供版本整併。

初次同步、少量修改、跨裝置分歧、整批修改與完整還原須分開量測。記錄端到端時間、請求數、傳輸量、本機處理時間及介面反應；尚無真實雲端效能結果，不宣稱改善倍數或固定秒數。

## 5. 文件與任務關聯

### 5.1 概念資料

| 記錄 | 用途 | 需要的資料方向 |
| --- | --- | --- |
| 文件來源 | 辨識外部檔案，供多個任務共用 | Orbit 文件識別、服務、來源範圍、服務端檔案識別（若有）、開啟連結、必要的類型與名稱／位置資訊 |
| 任務－文件關聯 | 描述哪個任務連結哪份文件 | 獨立關聯識別、任務識別、文件識別；用途、別名及排序欄位待設計 |
| metadata 快取 | 顯示已取得的檔名、位置與狀態 | 最後已知資訊、檢查時間及狀態；持久資料與可重建快取的界線待設計 |
| 服務連線 | 執行目前裝置可使用的服務操作 | 授權與連線狀態獨立保存，不放進工作資料／備份；不以暫時連線識別取代文件的來源身份 |

服務端識別是外部文件的身份，不等於 Orbit 任務或關聯的識別。從文件找任務應查詢同一份關聯記錄，避免額外維護另一份容易不一致的反向清單。

### 5.2 已同意的五個行為

1. 從任務移除連結只解除關聯，不刪除雲端原檔。
2. 複製任務或匯入工作空間副本，預設仍指向原外部文件，不複製文件內容。
3. 兩台裝置各新增不同來源文件時，整併後保留兩份；若指向同一份來源文件，文件來源記錄應去重，同一任務也不重複出現同一文件關聯。
4. 自動刷新檔名、路徑等 metadata，不算使用者編輯任務，不因純快取更新重複建立 Orbit 雲端版本。
5. Orbit 備份保存文件來源與任務關聯，不保存雲端文件內容。

同一文件可以連結不同任務，文件去重不能阻止建立其他任務或其他任務的關聯。手動修改任務內的文件別名／用途則屬於工作資料變更，與服務端自動刷新 metadata 分開處理。

關聯新增及移除須能按各自識別同步。晚到的舊版本不能復活已移除的關聯；刪除標記及同一關聯相互衝突的處理細節待設計。

### 5.3 文件去重：識別碼優先已定案

已定案的是按「連結的檔案來源」判斷同一文件，不比較內容或內容雜湊。不在不同雲端服務之間依內容去重。

已確認採用「識別碼優先，路徑與檔名作為備援」：有服務端穩定識別時，以「服務＋該服務的來源範圍＋檔案識別」判斷；只有缺少識別碼時才使用完整路徑與檔名等可確認的來源定位資訊，不比較文件內容。

「來源範圍」按服務決定，可能是雲端硬碟、帳號或地區；不能把 Orbit 分頁中的登入序號當成來源範圍。同一檔案被不同已授權帳號看到時，也不應僅因連線不同就自動變成不同文件。

| 情境 | 已確認的處理原則 |
| --- | --- |
| 同一來源識別，不同檔名或路徑 | 視為同一文件，更新顯示資訊 |
| 不同來源識別，相同檔名或路徑 | 保留為不同文件，避免誤合併 |
| 沒有來源識別，完整路徑及檔名相同 | 只在能確認來源範圍與該服務定位規則時採用備援比對；有歧義則保留待辨識 |
| 不同服務或不同來源範圍，名稱與路徑相同 | 保留為不同文件 |
| 沒有來源識別與完整路徑 | 保存可用連結，避免只按檔名強行合併 |

服務端位置不是永久身份。pCloud 官方建議使用 fileid／folderid 而非完整路徑；Microsoft 的 ID 定位也與路徑定位分開。各服務的重新命名、移動、複製及跨雲端硬碟移動行為須另外驗證。[pCloud 來源定位](https://docs.pcloud.com/)、[Microsoft 雲端項目定位](https://learn.microsoft.com/en-us/graph/onedrive-addressing-driveitems)

## 6. 任務與側欄流程

### 任務中加入既有文件

從任務的「加入文件」選擇來源文件，建立關聯後顯示文件名稱、來源服務與可確認的位置。文件可來自不同已連接服務。位置顯示保留原規劃，但完整路徑不可取得時的顯示方式尚待決定。

### 任務中建立文件

已定案順序：選擇雲端服務與該服務支援的檔案類型 → 選擇雲端保存位置 → 建立文件 → 保存任務關聯 → 開啟服務的外部編輯／檢視入口。

檔名輸入、預設名稱、預設資料夾及記住上次選擇的規則尚未定案。服務只顯示它能支援的建立類型；Google 首批目標為 Google 文件、試算表與簡報，不假設每個服務提供相同編輯能力。

### 從側欄文件建立任務

側欄列出文件，每份文件提供「建立任務」按鈕，亦可拖曳到支援的新任務落點。建立成功後，任務自動連結拖曳或點選的來源文件，文件內容不複製進任務描述。

側欄文件亦可作為任務「加入文件」的來源。拖曳到既有任務時應建立文件關聯，與拖曳到新任務落點區分；具體落點、預設任務欄位及多選行為待設計。

從側欄文件查看相關任務使用同一份關聯資料；查找的工作空間範圍與完成／封存／垃圾桶任務的呈現方式尚待決定。

### 側欄目錄導航需求（已確認）

使用者希望在 Orbit 右側側欄直接打開自己的 Drive 目錄，導航至所需檔案，再將檔案拖到主畫面建立任務。因此產品目標是能瀏覽帳號可存取的目錄與檔案，不侷限於已連結 Orbit 任務的文件。我的雲端硬碟、共用項目及共用雲端硬碟的首版入口仍需細化。

完整目錄導航不等於初次連線就下載全部目錄。建議按目前開啟的資料夾讀取直接子項目，支援分頁與返回上層；檔名搜尋、常用位置及是否限制顯示資料夾仍待介面設計。Drive 的父資料夾查詢只回傳直接子項目，沒有單一請求遞迴列出全部子樹的參數。[Drive 目錄查詢](https://developers.google.com/workspace/drive/api/guides/search-files)

側欄列表快取及瀏覽狀態與永久文件關聯分開設計，避免把未連結的大量雲端檔案列表都加入全部工作空間備份。

### Google 授權邊界與建議方案（尚未定案）

依 Google 公開的標準 OAuth scopes，沒有能指定任意使用者資料夾、遞迴授權其全部既有與未來子檔案，並同時由 Google 阻擋其餘資料夾的 scope。`drive.file` 是 Orbit 建立或使用者明確授權檔案的範圍；不能把選取一個資料夾當成其全部子檔案都已取得內容讀寫授權。`drive.appfolder` 指應用程式專用資料，亦不是任意使用者資料夾的隔離權限。這是根據官方 scope 定義的設計判斷。[Google Drive 權限](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)

建議將「瀏覽 metadata」與「備份／建立文件」分別設計：

| 用途 | 建議權限或流程 | 實際邊界 |
| --- | --- | --- |
| Orbit 自製側欄目錄導航 | 按需取得 `drive.metadata.readonly` | 可讀取帳號可存取檔案的 metadata；此 scope 本身不能讀取內容或修改檔案 |
| 拖曳來源檔案建立／關聯任務 | 使用已有 metadata 保存來源識別及開啟連結 | 不因拖曳而另外授予該既有檔案內容讀寫權限 |
| Orbit 備份與新文件建立 | 沿用 `drive.file`，僅處理 Orbit 建立或明確授權的項目 | 對其涵蓋項目仍有相應讀寫能力，不能宣稱整個應用程式完全沒有內容存取權限 |
| 指定既有資料夾建立文件 | 檢查資料夾能力與應用程式授權；必要時透過 Picker 選取授權位置 | metadata 唯讀權限不代表能在該資料夾建立文件，也不擴張為全部子檔案內容權限 |
| 限制側欄顯示某資料夾 | 在 Orbit 設定根位置及查詢／導航範圍 | 屬於 Orbit 的介面與請求限制；metadata token 的授權範圍不因此縮小 |

Google 官方明確區分 metadata 與內容：`drive.metadata.readonly` 本身只讀 metadata，不允許下載文件內容或修改檔案。若同時取得 `drive.file`，其逐檔能力仍存在；增加唯讀 metadata scope 不會取消已有的檔案權限。[Google metadata 說明](https://developers.google.com/workspace/drive/api/guides/file-metadata)

此建議符合自製目錄導航與原檔內容留在服務端的需求，但 metadata 本身仍可能包含敏感檔名及位置。建議只讀取目錄、類型、識別及開啟連結所需欄位，按目錄載入，不讀取外部文件本文或內容縮圖，不建立全盤持久索引，也不將列表快取加入 Orbit 備份。文件瀏覽按使用者啟用時取得權限，備份入口不因這項瀏覽需求自動提高授權；實際 token 的範圍仍須檢查，不能只憑介面分開就宣稱憑證權限已隔離。

備份的檔案辨識及清理必須繼續限制於 Orbit 工作資料，不因憑證可看到更多 metadata 而把其他文件加入備份管理清單或刪除範圍。

`drive.metadata.readonly` 被 Google 列為 restricted scope。正式對外授權前須評估 Google 的應用程式驗證要求；若將相關資料保存於伺服器或傳送至伺服器，官方另有安全評估規則。維持純前端不代表所有審查需求自動消失。[Google scope 分類與驗證規則](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)

另有兩個可比較的方案，均尚未選定：

- Google Picker 搭配 `drive.file`：由 Google 介面瀏覽，使用者選取後把檔案放入 Orbit 側欄，再從 Orbit 項目拖曳建立任務。應用程式的逐檔授權較集中，但不是目前希望的完整自製目錄導航；選取檔案的逐檔授權也不等於 metadata 唯讀。官方支援在 web app 嵌入 Picker，沒有據此保證 Picker 內的檔案可直接跨框架拖曳至 Orbit。[Google Picker 整合](https://developers.google.com/workspace/drive/picker/guides/web-picker)
- 專用 Google 帳號只接收指定資料夾的分享：以該帳號的實際檔案存取權限形成來源邊界，配合合適的 OAuth scope；帳號仍可存取其自己建立或其他被分享的項目，需維持該帳號的使用範圍。這會增加帳號與資料夾分享管理成本。[Google 資料夾分享與權限](https://developers.google.com/workspace/drive/api/guides/manage-sharing)

## 9. 後續實作前的驗收要求

- 既有全部工作空間備份、跨分頁協調、離線保存及版本整併語意保留。
- 本機儲存升級中斷不丟資料；新 JSON 可獨立還原，舊備份可讀，選定工作空間匯出不留下缺失的文件參照。
- 匯出與清理須考慮任務垃圾桶、待選版本及仍需保留的已選用紀錄所引用的文件關聯，避免只看目前任務清單就丟失參照。
- 驗證不同任務各新增文件、同一任務新增不同文件、同一來源重複加入、同一關聯新增／移除並行，以及相互衝突的關聯修改。
- 任務與文件兩側查找一致；同一文件關聯多個任務，解除其中一份不影響其他任務及雲端原檔。
- 多服務同時連線不混用來源位置或授權；建立文件期間切換任務、帳號或資料世代，不把晚到結果寫入錯誤任務。
- 文件導航驗證目錄分頁與返回上層、唯讀 metadata 的能力邊界、指定位置建立所需授權，以及拒絕額外瀏覽權限時仍保留既有備份功能；建立關聯不額外授權既有文件內容讀寫。
- 新版本缺少區塊或校驗失敗時不套用；中斷可重試；並行分支保留；歷史清理不刪除保留版本依賴。
- 真實服務驗證側欄列檔、授權範圍、指定位置建立、外部開啟、失敗恢復與跨裝置同步；本機模擬測試不替代實際服務驗收。
