## 規劃邊界與既有基礎

- 檔案服務本輪只實作 Google Drive 多來源；pCloud、Microsoft 365／Office 365 只預留資料與服務介面，不加入實際連線或佔用主要操作入口。
- 維持以任務為中心的多對多關聯、逐層列表導航、獨立選檔狀態、檔案／郵件拖曳，以及外部文件內容留在原服務的原則。
- 文件來源、任務關聯、連線設定與可重建的顯示快取分開。更換連線不改變檔案身份，解除關聯不刪除原檔。
- Orbit 工作資料的遠端備份與檔案來源各自管理。新增檔案來源不切換備份帳號，也不擴大備份清理的檔案範圍。
- 維持離線任務操作、單一 JSON 匯出／還原、全部工作空間同步及既有衝突保護。後端更新憑證是獨立的架構決策，不隱含在一般介面改版內。

規劃起點已有來源身份、關聯事件、移除標記及格式 6 備份，當時 metadata 快取主要由瀏覽列表更新。交付至第三階段已改為看板格式 6、備份格式 7，以及跨畫面共用的按需查驗；歷史設計細節見[第一階段紀錄](task-document-phase1.md)。

## 1. 多個檔案來源

### 使用方式

「設定 → Google Drive」新增來源清單。每個來源可設定顯示名稱、Google OAuth Client ID，並分別連線、重新授權或解除連線。帳號身份以 Google 回傳結果確認；Client ID 是應用程式識別，不是 Google 帳號或雲端硬碟識別。

新增來源時可沿用主要 Client ID，也可填入其他 Client ID。同一帳號使用不同 Client ID、不同帳號使用同一 Client ID，都屬於需支援的情境；各 Client ID 仍須允許目前網站來源。

側欄與選檔視窗在列表上方提供精簡的來源切換，之下保留「我的雲端硬碟／與我共用」、搜尋及路徑的既有順序。用來源名稱辨識目前連線，帳號及 Client ID 詳情放在設定或提示中，不恢復大幅佔位的帳號標頭。

側欄、選檔視窗各自記住每個來源的目錄與搜尋，切換來源不相互跳動。不同來源失敗或到期時只影響該來源；任務既有連結與其他有效來源繼續可用。

### 身份、授權與遷移

- 新增穩定的本機連線設定識別 `profileId`，保存 `provider`、顯示名稱、Client ID 與預期帳號等公開設定。它用來選擇操作連線，不作為文件身份。
- 沿用現有 `google-drive`、`gmail`、`pcloud`、`microsoft-365` 服務識別。未串接的服務只有資料預留，不假裝可瀏覽。
- Google Drive 同一檔案被不同已授權帳號看到時，仍以現有 Drive 檔案識別去重；改名、搬移或換 Client ID 不另造一份來源。同名但不同 ID 的檔案保留為不同項目。
- 不同帳號看見的路徑、權限及查驗結果可不同，存於各連線的查驗快取。某來源無法存取，不得覆蓋另一來源成功的結果。
- 服務介面自行處理來源範圍；為未來服務預留帳號、區域、租戶與雲端硬碟等可選定位資料，不先假定所有服務的檔案 ID 都是全域唯一。
- 現有單一 Drive 瀏覽連線遷移成預設來源，保留已確認身份及未過期授權的原期限。既有任務來源 ID、URL 與關聯事件不重新編號。
- 憑證驗證繼續涵蓋 Client ID、帳號、權限、資料世代及失效識別。多來源的保存鍵、分頁訊息與請求取消必須隔離；不得因新增來源而讓舊分頁恢復已解除的連線。

主 Google 連線的「一次授權全部服務」維持同一 Client ID 下的流程。額外的檔案來源由自己的入口授權；不同 Client ID 不能假設由同一次授權一併完成，也不在背景連續彈出多個視窗。

## 2. 減少 OAuth 提示與背景更新 token

### 已核對的限制

Google GIS 支援 `prompt: ''`，可減少已授權使用者被再次提示；已知目標帳號時可搭配 `login_hint`。兩者是改善授權互動的參數，不保證任何帳號、瀏覽器或權限變更情境都沒有視窗。[Google JavaScript API](https://developers.google.com/identity/oauth2/web/reference/js-reference)

目前採用的瀏覽器 Token Model，官方要求 token 到期後由按鈕等使用者操作呼叫 `requestAccessToken()`。因此，**不能把定時器搭配 `prompt: ''` 規劃成可靠的無互動背景續期**，也不能自行延長已發出的 token 期限。[Google Token Model](https://developers.google.com/identity/oauth2/web/guides/use-token-model)

### 本輪建議：先改善現有前端流程

| 情境 | 建議行為 |
| --- | --- |
| 首次連線、增加來源、明確切換帳號 | 提供正常帳號選擇與必要同意流程 |
| 使用者點擊既有來源的重新授權 | 採 `prompt: ''`，在已知帳號時提供 `login_hint` |
| Google 要求登入、同意或無法開啟視窗 | 顯示可重試的來源提示，保留本機修改，避免反覆自動彈窗 |
| token 接近期限或已過期 | 顯示來源狀態及續接入口；未到期的其他服務繼續運作 |
| 取得新 token | 再驗證帳號與實際 scope，確認後才啟用該來源及接續可執行的工作 |

`login_hint` 不能取代帳號驗證。回傳帳號與來源原本綁定不同時，需讓使用者明確選擇換帳號，不能默默把來源改接到另一個雲端硬碟。

### 若要真正無互動續期

需另設後端，採 Authorization Code／離線授權流程，由伺服器取得並保存 refresh token，再按需更新 access token；GitHub Pages 的靜態前端本身不足以提供這個能力。[Google Code Model](https://developers.google.com/identity/oauth2/web/guides/use-code-model)、[離線授權與 token 更新](https://developers.google.com/identity/protocols/oauth2/web-server)

這條路線須另行定案：

- 後端部署位置、使用者登入與資料保管責任；refresh token、必要的 Client Secret 不放進前端設定、localStorage、工作資料或備份。
- 多個自備 Client ID 如何在後端完成相應的應用程式設定；不能把某一 Client ID 的 refresh token 拿去替另一個 Client ID 換取授權。
- 憑證撤銷／失效、帳號切換、來源移除及同步登出時的清除規則；授權失效仍須有重新連線路徑。
- 更新 access token 與背景執行 Orbit 備份是兩件事。即使能更新 token，關閉前端後要持續備份，仍需另外規劃工作資料如何交給後端及執行排程。

建議先交付前端重新授權體驗，其餘功能可繼續開發；若「完全免互動續期」成為本輪必要條件，先完成後端方案決策，再排入獨立里程碑。

## 3. 從任務建立文件，以及外部連結圖示

### 3.1 先改善目前的資訊連結

任務編輯模式的每一項檔名／郵件主旨後加入 ↗ 圖示，文字與圖示一起形成原來源連結，提示「在新分頁開啟」。圖示緊跟名稱；長名稱換行時仍可辨識，鍵盤焦點與觸控範圍完整。

沿用安全 URL 驗證與 `target="_blank"`、`rel="noopener noreferrer"`。無法安全開啟的舊範例資料保留可讀名稱，不出現可操作的外部連結。外開不修改任務、不取消草稿，也不把檔名點擊改成另一種隱藏操作。

### 3.2 建立文件的首批範圍

先提供 Google 文件、試算表與簡報；空白文件建好後交給 Google 編輯。Colab／ipynb 或其他檔案模板待另行定義，不因已有類型圖示就視為已有建立能力。

建議流程：

1. 從已保存任務的「資訊連結 → 建立文件」進入。新任務或仍有未儲存的任務變更時，先提供明確的「儲存任務並繼續」，不默默保存或丟棄草稿。
2. 選擇來源、檔案類型、名稱及保存資料夾；名稱預設使用任務名稱，允許修改。保存位置記住每個來源上次成功的位置，不使用 Orbit 備份資料夾作預設。
3. 按「建立並連結」後才取得必要的建立權限並執行；操作中防止重複點擊。
4. 建立成功後保存來源及任務關聯，顯示 ↗「開啟新文件」。若瀏覽器阻擋非同步開窗，保留這個可點擊入口。

`drive.metadata.readonly` 只供瀏覽，建立需另取得相應權限；首選評估 `drive.file` 與使用者選定位置。`files.create` 支援此 scope，但還須核對目標資料夾的實際能力及應用程式可存取範圍，必要時用 Google Picker 選取授權位置。額外來源須使用自己的 Client ID／帳號授權，不直接套用主備份帳號的權限。[Drive files.create](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/create)、[Drive 授權範圍](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)

### 部分成功與復原

| 情境 | 設計要求 |
| --- | --- |
| 拒絕建立權限或取消建立前的選擇 | 保留任務及原連結，不建立檔案 |
| 雲端檔案已建立，但本機關聯保存失敗 | 保留新檔 ID／URL 與操作記錄，提供重新加入；不得再次建立一份 |
| 請求逾時，不確定 Google 是否已建立 | 先查核該次操作；無法確認時提供查核入口，不盲目重送建立 |
| 操作期間任務被刪除、切換帳號或資料世代改變 | 停止寫回原任務，保留可辨識的建立結果與補救入口 |
| 建立完成後使用者解除關聯 | 沿用解除 Orbit 關聯的規則，原 Google 檔案保留 |

實作前先驗證原生 Google 文件的操作識別與重試方式，不假設所有類型都能預先指定檔案 ID。建立結果須與 Orbit 備份檔的識別、列表及清理範圍分開。

## 4. 已連結檔案的名稱與位置更新

### 共用更新機制

由共用 metadata 服務處理側欄、選檔、任務編輯與未來總覽所需的檔案資訊。列表導航與選取狀態仍各自獨立；同一來源、同一檔案的查驗可共用快取及正在進行的請求。

畫面先呈現最後已知的名稱與位置，再背景查驗過期的可見項目。改名或搬移只更新顯示快取，不改任務名稱、任務修改時間或關聯身份，也不因每次查驗產生一個 Orbit 備份版本。

檔名、類型及原來源連結優先採服務端資料；路徑按可存取的父資料夾重建。父資料夾改名或搬移，也要讓已知相關路徑失效。無法讀取完整祖先時顯示「部分位置／無法取得完整路徑」，不把側欄曾經的瀏覽路徑當作永久真實位置。捷徑的所在位置與目標檔案位置分開處理。

### 建議的請求策略

| 觸發 | 行為與建議起點 |
| --- | --- |
| 已取得新的側欄／選檔列表 | 順便更新已知項目，不再為同一批檔名補發逐檔請求 |
| 開啟任務 | 立即顯示快照，只排程目前可見且過期的檔案查驗 |
| 一般查驗 | 成功結果暫定 15 分鐘有效；大量連結分批排程，每批先處理 20 項 |
| 多個畫面引用同檔 | 合併相同授權範圍下的進行中請求，每個來源並行 2 筆、全體先限制 4 筆 |
| 取得父資料夾路徑 | 重用父項快取，限制追溯深度與每輪額度；到上限先顯示部分位置 |
| 手動「更新連結資訊」 | 可略過 TTL，仍遵守去重、並行與退避限制，並顯示查驗結果 |
| 背景、離線或授權失效 | 暫停自動查驗，保留上次資料；恢復後只排程需要的項目 |

上述批次是排程單位，不能把 20 份檔案當成只消耗一筆 Drive 查詢。只要求必要欄位，不下載內文、縮圖或整份硬碟索引。快取以資料世代、來源／帳號、授權範圍與文件身份隔離，避免跨來源誤用權限結果。

首次先做按需查驗。其後再依量測決定是否加入 `changes.getStartPageToken`／`changes.list` 增量追蹤：它可能包含大量與 Orbit 無關的帳號變更，並非只回傳已連結檔案。只處理已知連結與路徑所需祖先，設每輪頁數額度；整頁處理成功後才保存游標，未處理完的頁保留進度。[Drive 變更追蹤](https://developers.google.com/workspace/drive/api/guides/manage-changes)、[changes.list 權限](https://developers.google.com/workspace/drive/api/reference/rest/v3/changes/list)

驗證時分開記錄冷／暖快取的請求數、傳輸量、等待時間及命中率。例如十張任務引用同一檔案，不得變成十筆同時查驗；全部命中有效快取時不應發出 metadata 請求。這些是待驗收目標，不是已取得的效能結果。

## 5. 檔案失效與未查驗提示

沿用第 4 節的更新機制，不再為失效檢查另設一套逐檔輪詢。每筆結果保存最後成功資料、最後檢查時間及原因，畫面區分：

| 狀態 | 顯示與處理 |
| --- | --- |
| 可存取 | 顯示目前名稱、可確認位置及查驗時間 |
| 尚未查驗／資料過期 | 顯示保存快照，清楚標示尚未確認最新狀態 |
| 離線／網路錯誤 | 保留名稱與連結，等恢復連線或手動重試 |
| 該來源需要授權 | 提供該來源續接入口，不宣稱檔案已失效 |
| 明確回傳在垃圾桶 | 顯示「已移至垃圾桶」，保留關聯與原服務入口 |
| 無法存取／找不到 | 顯示「可能已刪除或權限變更」，提供更新、換來源查驗及解除關聯 |
| 配額／服務忙碌 | 限速與退避重試，不改標為檔案不存在 |

Google 的 404 同時可能表示沒有讀取權限或資源不存在，不能僅憑它斷言檔案已刪除；403 也須依錯誤原因區分權限與限流。[Drive 錯誤處理](https://developers.google.com/workspace/drive/api/guides/handle-errors)

失效檔案仍計入任務實際保留的資訊連結數，另標示需處理項目；不能因請求失敗就自動解除。相同文件若有另一個來源仍可讀取，顯示其成功結果並指出可用來源。郵件不直接套用 Drive 的失效判斷，Gmail 主動查驗另排範圍。

## 6. 資訊連結的說明與手動排序

每個任務可為自己的連結填寫用途說明，例如「會議前要閱讀的資料」。說明屬於任務－來源關聯，同一文件連到不同任務時可不同；不改 Google 檔名或 Gmail 主旨，也不提供自訂別名。

建議首版用純文字說明，長度上限先設 1,000 字；空白不佔額外行。來源名稱與 ↗ 保持外開連結，說明使用自己的編輯按鈕，避免混淆點擊用途。

資訊連結區提供拖曳排序及鍵盤可操作的上移／下移按鈕；檔案、資料夾、郵件使用同一份順序，新加入項目排在最後。編輯及排序先更新草稿，儲存任務後生效；取消保留原說明與順序。

資料設計須處理現有「同一任務／文件可能有多個新增事件，但畫面只呈現一次」的情況。建議另設邏輯關聯的呈現資料，保存說明與穩定排序值，保留原新增事件及移除標記；不直接按來源陣列的位置排序，也不讓重複事件顯示兩份說明。

不同關聯的說明可安全整併；同一說明或順序被兩台裝置同時改動時，以共同基準判斷，保留不能安全整併的候選內容，不以裝置時間覆蓋。復原／重做、任務複製、工作空間副本及 JSON 還原均須涵蓋說明與排序。解除後再新增與復原舊關聯的呈現資料生命週期，在格式定案時一併明訂。

## 7. 來源紀錄清理

先區分「清除可重建快取」、「整理無使用來源」與「解除服務連線」。三者不是同一個操作；都不直接刪除 Google 原檔。

來源是否仍被使用，要檢查所有工作空間的有效任務、垃圾桶、衝突候選、復原／重做、未完成建立操作及保留的關聯事件。清理前在寫入協調下重讀，期間出現新引用就取消該項清理。

建議分兩層交付：

1. **安全整理**：先回收過期列表／查驗快取，列出無目前有效引用的來源；必要時將來源標記退役、縮減顯示快照，保留仍被歷史事件需要的身份資料。
2. **永久壓縮**：等來源退役格式、移除標記與舊裝置接續規則完成後，才評估實體刪除。不能只因「已經過了幾天」就丟掉防止舊版本復活的標記。

目前讀取器要求關聯指向有效來源，不能直接刪除來源、留下懸空事件。新格式須能讀取必要的最小歷史身份，並保護仍需還原的版本。已匯出的備份及雲端歷史不因本機整理而被改寫；舊備份還原可能帶回舊來源紀錄，屬於還原語意，不應連帶刪除使用者歷史。

設定中的整理入口先顯示可回收範圍及仍受保護的原因；快取整理可直接重建，會影響可還原內容的永久壓縮則另設確認。來源解除後，任務連結保留可讀快照與外開入口，查驗狀態變為需重新綁定。

## 8. 寬畫面任務編輯雙欄

任務編輯在可用寬度足夠時放大，右欄依序放資訊連結、任務時程與子任務。保留目前名稱左側的釘選、精簡標頭、分類／狀態配色及各區外框。

| 左欄：主要內容，約 60% | 右欄：約 40% |
| --- | --- |
| 任務名稱與釘選 | 資訊連結：外開、說明、排序、選檔及建立文件 |
| 專案、分類、目前狀態與優先順序 | 任務時程 |
| 任務描述及 Markdown 編輯 | 子任務 |

尺寸先以最大寬 1,200 px、視窗左右各保留約 24 px 為起點。是否切雙欄看實際容器與字級，左欄至少約 520 px、右欄至少約 320 px；不足時回單欄，不因螢幕像素多就強制擠入兩欄。

表單採一個主要垂直捲動區，標頭與儲存／取消列保持可及，避免左右各一條長捲軸。窄畫面維持熟悉的單欄順序。縮放、調大字體或旋轉裝置不重建表單、不清除草稿；鍵盤順序符合閱讀順序。描述專注編輯及獨立選檔 modal 保留，往返不遺失其他欄位。

## 9. 甘特視圖

加入與看板、清單、月、週並列的甘特入口，沿用目前工作空間、專案、分類、狀態及任務篩選。首版只顯示 Orbit 任務，避免把外部 Calendar 活動混成可編輯任務。

### G1：先交付可閱讀、可開啟任務的視圖

- 左側任務名稱與狀態／專案，右側按日期排列時間條；提供今日定位及日、週、月的顯示尺度。
- 同時有開始與截止日期：顯示含起訖日的區間；只有一端日期：顯示單日標記並標示「僅開始／僅截止」，不捏造另一端。
- 無日期任務放在「未排程」區，保留開啟編輯入口。既有時間值在提示及任務編輯中可見，日尺度不刪掉時間。
- 點時間條或任務名稱開啟同一個任務編輯器。保留已完成／封存的既有篩選與逾期語意。
- 大量任務採可見列與可見日期範圍渲染；手機可水平捲動時間軸，任務名稱仍可辨識。

### G2：再加入時間操作與來源拖曳

整條拖移保留區間長度與原時間，兩端調整只修改對應日期，沿用日期驗證及復原／重做。日期按日曆日計算，避免用固定 24 小時毫秒數處理跨時區／夏令時間邊界。

檔案／郵件拖到既有任務條時加入資訊連結；拖到明確的新任務列及日期 placeholder 時建立帶日期的任務，沿用已完成的來源驗證、取消、觸控與邊緣捲動。先把移動任務、拉長時程與拖入來源的手勢分清楚，再開放編輯操作。

任務相依線、前置／後置延遲、關鍵路徑與自動排程屬於後續範圍；本輪不因加入甘特顯示就替任務新增未定義的相依規則。

## 10. 左側「空間總覽」與 Dashboard

在左側專案看板的待完成／已完成入口上方新增「空間總覽」。選取後主區域呈現目前工作空間的任務 Dashboard，切換工作空間時更新；首版不混入所有工作空間的統計。

### 首版內容

| 區塊 | 建議內容 |
| --- | --- |
| 概況數字 | 有效任務總數、待完成、已完成、逾期、未排程及有資訊連結的任務數 |
| 狀態分布 | 依實際自訂狀態與顏色顯示，完成語意依 status kind 判斷 |
| 專案概況 | 各專案及未指定專案的任務數與完成比例 |
| 時程重點 | 今日／本週開始、即將截止及逾期任務入口，沿用既有日期規則 |
| 需要處理 | 衝突任務；已查驗且無法存取的連結另顯示數量與查驗覆蓋，未查驗不算失效 |

統計預設排除垃圾桶、封存任務及封存專案，與現有整體專案進度一致；可另外選擇檢視封存範圍。空間總覽有自己的專案篩選，不因之前停在「已完成任務」就讓整份 Dashboard 只剩已完成資料。

完成率定義為已完成／有效任務總數。例如有效任務 8 項、完成 3 項為 37.5%，畫面可沿用整數顯示為 38%；沒有任務時顯示空狀態及 0%，不產生無效比例。子任務完成數另列，不混入主任務分母。週區間、全天截止與含時間的逾期判斷，統一沿用既有時程工具。

點數字或圖表項目後，進入套用對應條件的清單／看板，並顯示篩選條件；必須能返回總覽。統計由本機工作資料衍生並快取，不為 Dashboard 掃描 Drive，也不另存一份容易不同步的統計資料。

首版不提供需要歷史事件才能正確計算的燃盡圖或「每天完成幾項」趨勢。目前任務最後修改時間不等於完成時間；若後續要做這類圖，先設計完成事件、重新開啟及復原的紀錄。

## 11. 資料與服務介面的準備

以下為概念分層，欄位與格式版本在實作前定案，不直接視為已變更的 schema。

| 資料／介面 | 保存與責任 |
| --- | --- |
| 檔案連線設定 | 本機公開設定：profileId、provider、名稱、Client ID、預期帳號及可選服務定位。完整 JSON 可評估提供明確選項攜帶公開設定；日常同步不覆蓋其他裝置的連線 |
| 授權狀態 | 本機獨立保存有效憑證、權限與期限；如採後端，refresh token 只在後端保管。授權不進工作資料或備份 |
| DocumentSource | 沿用穩定來源身份、URL 與離線快照；額外定位由 provider 定義，不綁暫時 session 或某個本機 profileId |
| DocumentLink | 繼續保存新增事件與移除標記，讓晚到版本不能復活已移除事件 |
| 邏輯關聯呈現資料 | 每個任務／來源的說明、排序及必要的生命週期識別；同一來源在不同任務可有不同說明 |
| MetadataRepository | 可重建的 IndexedDB／記憶體快取，保存名稱、位置、查驗狀態及連線範圍；不參與任務同步雜湊 |
| ProviderAdapter | 列表、取得 metadata、開啟 URL；建立文件、增量游標為可選能力。pCloud／Microsoft 365 先只留介面，不提供假資料 |
| 請求排程與建立操作記錄 | 去重、並行額度、退避、取消及建立結果復原；與工作資料及 UI 導航狀態分開 |

快取清除後仍須能從來源快照開啟連結；跨裝置看到新名稱的時機由各裝置重新查驗決定，避免為了同步顯示名稱而反覆發布工作版本。新裝置匯入任務後須自行連線可存取的來源，本機連線識別不能使連結變成孤兒。

目前讀取器會挑選已知欄位，不能只添加說明／排序後就假定舊版可保存。新工作資料、JSON、IndexedDB 紀錄、分塊同步、雜湊與整併須一起遷移；支援讀舊格式，新格式則阻止不理解欄位的舊程式寫回。來源 ID、移除標記與歷史校驗保持相容，不在讀取舊備份時補寫資料破壞原校驗。
